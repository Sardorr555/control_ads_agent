## 1. Введение и контекст риска (WHY & Financial Zero-Trust)

Трек **v3 (Ads Automation Agent)** принципиально отличается от треков v1 (Email Outreach) и v2 (CIS Data Scraping).
В предыдущих треках максимальный ущерб от ошибки агента сводился к испорченной репутации домена рассылки или временному бану по IP. 

В треке v3 **агент взаимодействует с реальными рекламными бюджетами и платежными шлюзами**.
Неконтролируемая ошибка в коде, галлюцинация LLM в установке ставки, циклический вызов API или неверно поставленная запятая в бюджете могут привести к **моментальному списанию тысяч долларов с корпоративной карты**.

Поэтому для данного трека устанавливается архитектурный принцип:  
**Zero-Trust Financial Architecture (Нулевое доверие к агенту в финансовых операциях)**:
1. Агент **никогда** не имеет права активировать показ рекламы (`status: ACTIVE` / `state: ON`) самостоятельно.
2. Любая кампания создаётся **только в изолированном / остановленном виде** (`PAUSED` / `DRAFT` / `OFF`).
3. Для боевого запуска необходим криптографически / журнально фиксируемый **Human Approval Gate** (`--confirm-budget-approval`).
4. На уровне рекламного кабинета **обязательно** должен быть выставлен аппаратный лимит платформы (Platform Hard Cap), блокирующий перерасход, даже если весь наш код аварийно упадёт.

## 3. Детальный разбор платформ и архитектурные риски

### 3.1 Google Ads API
* **Сильные стороны:**
  1. `validate_only=True` — лучший в индустрии механизм сухого прогона перед созданием любых сущностей.
  2. Глубокий таргетинг на горячий поисковый спрос (люди, которые сами ищут "внедрение ИИ", "RAG для банков", "автоматизация продаж").
  3. Тестовые аккаунты (Test Accounts) полностью имитируют рабочий кабинет.
* **Критические риски и ограничения:**
  1. **200% Pacing Rule:** Если агент назначит дневной бюджет $50, Google может списать в удачный день $100. Это требует установки искусственного занижения дневного лимита в коде (например, задавать $25, если целевой лимит $50).
  2. **Сложная бюрократия онбординга:** Получение Basic Access для боевого аккаунта требует прохождения верификации GCP и compliance-проверки. Без этого токен работает только с пустыми тестовыми аккаунтами.
  3. **Отсутствие UZS:** Оплата только в USD, закрывающие документы не интегрированы с Didox.

### 3.2 Meta Marketing API (Facebook / Instagram)
* **Сильные стороны:**
  1. **Instagram — рекламная площадка №1 в Узбекистане** для привлечения внимания бизнеса, фаундеров и топ-менеджеров.
  2. **Development Mode снимает необходимость App Review:** Для автоматизации рекламы собственного бизнеса SWIPIES достаточно создать системного пользователя (System User) с токеном доступа в Business Manager. Внешний 20-дневный аудит от Meta не нужен!
  3. **Account Spend Limit:** Наличие жесткого аппаратного `spend_cap` на аккаунте защищает от любых катастрофических перерасходов.
* **Критические риски и ограничения:**
  1. Нет нативного серверного флага `validate_only` для одиночных POST-запросов. Безопасность строится исключительно на жестком соблюдении `status="PAUSED"`.
  2. Качество официального SDK `facebook-business` низкое, частые предупреждения об устаревших методах, плохая типизация.
  3. Оплата только в USD, 12% НДС без локального счета-фактуры.

### 3.3 Yandex Direct API (v5)
* **Сильные стороны:**
  1. **Идеальная юридическая и финансовая чистота для Узбекистана:** Официальное юрлицо, прямая оплата в UZS по безналу с узбекского счета, электронные счета-фактуры через Didox/Soliq с официальным учетом НДС 12%.
  2. **Быстрый старт:** Получение доступа к боевому API занимает 1–3 дня, песочница доступна сразу.
  3. **Жесткий стоп по бюджету:** В режиме `STANDARD` кампания останавливается сразу при исчерпании лимита, без перерасхода.
  4. **Простота интеграции:** Чистый JSON API без монструозных SDK, легко покрывается Pydantic-моделями и тестами на 100%.
  5. **Огромный охват:** Высокая плотность B2B-аудитории в поиске Яндекса и сетях (РСЯ) в регионе Центральной Азии.
* **Критические риски и ограничения:**
  1. **Система баллов (Units):** Если код агента начнет генерировать частые ошибки валидации (400 Bad Request), суточный запас баллов быстро сгорит (штраф за ошибочные запросы). Нужна тщательная локальная валидация до отправки запроса.
  2. Отсутствие официального поддерживаемого SDK от вендора требует написания собственного аккуратного API-модуля (на `httpx`).

### 3.4 Анализ аудитории Узбекистана: Где реально принимаются решения в Enterprise B2B?

Критический вопрос выбора платформы — не только «где проще подключить API», но и **«где реально находится лицо, принимающее решения (ЛПР)?»**.

#### 1. Доли поискового рынка в Узбекистане (StatCounter 2025–2026)
* **Google:** **~73–76%** общего поискового трафика в Узбекистане.
* **Yandex:** **~22–25%** общего поискового трафика.
* **Специфика технической аудитории (CTO, Head of AI, Lead Devs):** В среде IT-специалистов, технических директоров и финтех-разработчиков Ташкента доля Google превышает **80–85%**. Поиск технической документации, GitHub, StackOverflow и профильных SaaS ведется исключительно через Google на Chrome/MacOS/Linux. В поисковую строку Яндекса технические ЛПР за enterprise-решениями практически не приходят.

#### 2. Главная «слепая зона» поисковой рекламы в B2B (Google vs Yandex)
**Ищут ли в принципе ЛПР в Узбекистане «AI для банков» через поисковую строку?**
По данным Yandex Wordstat и Google Keyword Planner по региону «Узбекистан»:
* Запросы вида *«AI для банков»*, *«RAG решения enterprise»*, *«ИИ поиск по документам»* имеют **околонулевую частотность (0–15 запросов в месяц)** на обеих площадках.
* Руководители банков (Ipak Yuli, Kapitalbank, Agrobank), финтех-фаундеры и партнеры юрфирм **не покупают сложный B2B-софт через контекстный поиск**. В B2B enterprise поискового спроса на инновационные технологии в ЦА ещё не сформировано — его нужно **формировать проактивно**.

#### 3. Где реально живет внимание деловой аудитории в Узбекистане:
1. **Meta (Instagram / Facebook) — Деловой канал №1 в Узбекистане:**
   В отличие от рынков США/ЕС, где B2B живет в LinkedIn, в Узбекистане **Instagram является главной бизнес-витриной**. Владельцы бизнеса, топ-менеджеры, банкиры и госслужащие ежедневно проводят в Instagram от 1 до 2 часов. Таргетированные кампании (Lead Generation / Traffic) по интересам *«Банковское дело, Финтех, Искусственный интеллект, Руководители высшего звена»* в Ташкенте показывают в 5–10 раз больший объем реальных лидов, чем контекстный поиск.
2. **РСЯ (Рекламная Сеть Яндекса):**
   В экосистеме Яндекса для B2B ценен не сам поиск, а **РСЯ на топовых деловых и новостных медиа Узбекистана** (Spot.uz, Gazeta.uz, Kun.uz, Daryo.uz, RBK). Размещение графических баннеров и статей через РСЯ с оплатой в UZS позволяет охватить директоров во время чтения утренних бизнес-новостей.
3. **Outbound (Track v1/v2) + Retargeting:**
   Холодный аутрич находит конкретного ЛПР, а реклама в Meta/РСЯ «догоняет» его брендовыми кейсами и формирует доверие перед созвоном.

## 4. Архитектура безопасности: 4 рубежа защиты бюджета

Для полного исключения финансовых инцидентов в кодовой базе агента закладывается 4-уровневая система защиты:

```
[Запрос пользователя / LLM]
           ↓
[РУБЕЖ 1: Локальная валидация Pydantic + Hard Budget Caps]
   (Проверка: бюджет не выше лимита в конфиге, обязательный статус PAUSED/DRAFT)
           ↓
[РУБЕЖ 2: Safe-Mode Dry-Run на платформе]
   (validate_only в Google, либо создание тестового объекта в Sandbox)
           ↓
[РУБЕЖ 3: Human Dual-Key Approval Gate]
   (Блокировка до явной команды человека с фиксацией в audit_log:
    --confirm-budget-approval="Имя, Дата, Кампания, Сумма_бюджета")
           ↓
[РУБЕЖ 4: Аппаратный лимит платформы (Platform Hard Cap)]
   (Выставление account-level spend_cap и campaign-level daily cap)
           ↓
[Активация кампании на платформе]
```

* **Аудит-лог:** Любая операция с бюджетом фиксируется в защищенном локальном SQLite-логе `ads_audit.db` с фиксацией IP, даты, хэша подтверждения и параметров кампании.
* **Circuit Breaker:** Фоновый процесс отслеживает текущий расход каждые 15 минут через API. Если скорость расхода (burn rate) превышает заданный порог, все кампании немедленно переводятся в статус `PAUSED`.

## 5. Рекомендация и дорожная карта (Roadmap)

### Реалистичный пересмотр с учётом поведения B2B-аудитории:

После детального анализа аудитории (п. 3.4) вырисовывается важный дуализм:
* **С точки зрения финансовой и юридической безопасности:** Лидирует **Yandex Direct** (оплата в UZS, Didox, нет оверспенда). Но в Яндексе мы должны ориентироваться **не на Поиск (где спрос нулевой), а на РСЯ (баннеры на Spot.uz/Gazeta.uz)**.
* **С точки зрения реального объёма B2B-лидов:** Лидирует **Meta Marketing API (Instagram)**. В Узбекистане это главная деловая соцсеть, где сидят фаундеры и директора. Внутренний аккаунт в Development Mode запускается без многонедельного ревью, а аппаратный `spend_cap` исключает финансовые риски.

#### Итоговая оценка:

1. **Meta Marketing API (Instagram / Facebook) — Максимум целевых лидов:**
   * **Плюсы:** Единственный канал с высокой конверсией в B2B-лиды в Ташкенте (Lead Ads / трафик на лендинг). Внутренний аккаунт не требует App Review. Есть аппаратный `spend_cap`.
   * **Минусы:** Оплата в USD (международная карта), нет локальных ЭСФ через Didox, отсутствие единого `validate_only`.

2. **Yandex Direct API (v5, фокус на РСЯ) — Максимум юридической чистоты:**
   * **Плюсы:** Безупречные закрывающие документы в UZS через Didox для бухгалтерии, отличная песочница Sandbox, быстрый аппрув API за 1–3 дня.
   * **Минусы:** Поисковый спрос на AI/RAG в РУз отсутствует; эффективна только контекстно-медийная сеть (РСЯ) на бизнес-порталах.

3. **Google Ads API — Глобальный масштаб (Приоритет v2):**
   * **Плюсы:** Превосходный `validate_only`, идеален для англоязычного B2B на США/Европу/MENA.
   * **Минусы:** Высокий риск потери денег на тестах из-за механизма Overdelivery (до 200% без компенсации на коротких кампаниях), сложнейший онбординг (GCP + Developer Token). Подключать строго вторым этапом при выходе за пределы СНГ.
